# 轻量化电子实验记录助手：项目概述

> 文档用途：明确产品定位、核心业务规则、第一版范围和主要边界情况，作为后续原型设计、需求拆分、数据库设计及 code agent 协作的依据。  
> 原始构思保留在根目录的 `overview_ideas.md`。  
> 当前阶段：项目构思与 MVP 需求收敛。  
> 最后更新：2026-07-22。

## 1. 产品定位

本项目拟开发一款面向高校学生实验、课程设计和初级科研训练的轻量化电子实验记录助手。系统借鉴 Benchling 等电子实验记录产品的组织方式，但不追求复刻专业科研平台，而是重点解决以下问题：

- 实验资料分散在 Word、聊天软件、本地文件夹中，难以统一组织。
- 学生记录格式不统一，容易遗漏实验目的、过程、结果等关键信息。
- 小组成员之间缺少清晰的职责、审核和修改追溯机制。
- 已完成实验难以搜索、复用和整理成课程报告。

产品核心价值可以概括为：

1. 以项目为单位组织实验记录和附件。
2. 通过模板降低规范记录的门槛。
3. 通过提交审核形成“撰写—反馈—修改—完成”的闭环。
4. 通过搜索、审计和导出提高实验资料的可查找性与可复用性。

### 1.1 目标用户

- 参与实验课程或课程设计的高校学生。
- 参与小型科研训练项目的学生团队。
- 负责指导、验收或审核实验记录的教师、助教或学生负责人。

### 1.2 非目标

第一版不计划实现以下能力：

- DNA、RNA、蛋白质序列分析等专业生物信息学功能。
- 试剂库存、仪器预约、采购和实验室资产管理。
- 多人实时协同编辑和光标同步。
- 面向药企合规场景的电子签名、法规认证和复杂审批流。
- 附件正文 OCR、Office 文档全文解析或图片内容识别。
- 原生移动端应用。
- 完整复刻 Benchling 的全部业务能力。

## 2. 核心术语与角色

原始构思中的“负责人”“成员”“审核者”容易在项目级和记录级之间混淆。后续界面、数据库、API 和测试统一使用以下术语。

| 术语 | 含义 |
|---|---|
| 项目参与者 | 项目负责人、编辑成员和审核者的统称 |
| 项目负责人（Owner） | 项目的唯一管理者，负责项目设置、成员和角色管理 |
| 编辑成员（Member） | 可以创建实验记录，并编辑自己创建记录的项目成员 |
| 审核者（Reviewer） | 默认只读，可以审核被明确指派给自己的实验记录 |
| 记录创建者（Creator） | 创建并唯一管理该实验记录的用户，创建后不可变 |
| 指定审核人（Assigned Reviewer） | 某一次提交审核时选择的审核人；审核轮次结束后仍保留在历史中 |

角色规则：

- 一个项目始终且只能有一名项目负责人。
- 同一用户在同一项目中只拥有一个项目角色。
- 记录创建者负责编辑、保存、管理附件、提交审核，以及在允许状态下删除记录。
- 项目负责人拥有项目管理权，但不能修改、提交或删除其他用户创建的实验记录。
- 创建实验记录时，创建者必须是本项目的项目负责人或编辑成员。
- 每次提交只能指定一名审核人。审核人必须是本项目的项目负责人或审核者，并且不能是该记录的创建者。
- 同一条记录同一时刻最多只能存在一个未结束的审核轮次。
- 审核者可以查看项目内容，但只有被指定后才能对某一轮提交执行“通过”或“退回修改”。
- 所有项目参与者都可以查看项目内各状态的实验记录，包括其他用户的进行中记录，但只有创建者可以管理记录内容。
- 所有权限必须在后端校验；前端隐藏按钮不能代替权限控制。

## 3. 领域结构

系统的主要层次仍为“项目—实验记录—附件”，但为了支持邀请、审核和追溯，需要补充成员关系、提交快照和审计事件。

~~~text
用户 ──< 项目成员关系 >── 项目 ──< 实验记录 ──< 附件
                         │          ├──< 提交快照
                         │          └──< 审核轮次
                         └─────────────< 项目审计事件

用户 ──< 个人模板
用户 ──< 站内通知
系统 ──< 系统模板
~~~

关键约束：

- 实验记录必须且只能归属于一个项目。
- 附件必须且只能归属于一条实验记录。
- 审核针对某次提交产生的不可变快照，而不是持续变化的编辑内容。
- 模板只是创建记录时的结构来源。记录创建后保存一份模板结构副本，后续修改或删除模板不能改变已有记录。

## 4. 功能范围与迭代优先级

### 4.1 MVP：第一版必须形成的闭环

- 用户注册、登录、退出和基本资料维护。
- 创建项目、查看项目、邀请成员和分配角色。
- 项目进行中和已归档两种状态。
- 使用空白结构、系统模板或个人模板创建实验记录。
- 编辑并保存进行中记录、上传附件、提交审核、退回修改和审核完成。
- 站内通知中心、未读状态和审核流程即时提醒。
- 搜索中心中的跨项目全局搜索、筛选和分页。
- 记录关键操作的审计事件。
- 预览并导出已完成的单条实验记录，支持 PDF 和 Markdown。

### 4.2 第二阶段功能
- 历史版本列表、内容差异对比和恢复。
- 项目级组合报告和 Excel 结构化数据导出。
- 项目共享模板。
- 真实邮件、短信或浏览器推送，以及定时、重复的逾期催办。
- 回收站、误删恢复和更完整的数据保留策略。

### 4.3 暂不实现

- 多审核人会签、并行审核和多级审批。
- 模板条件分支、计算字段、嵌套表格和可重复字段组。
- 附件内容全文检索。
- 实时协作编辑。
- 项目公开分享和匿名访问。
- 已完成记录的重新开启、修改和修正流程。

## 5. 功能需求与业务规则

### 5.1 用户与身份

#### USR-01 注册与登录

- 用户注册时必须填写用户名、邮箱和密码。
- 用户名用于系统内展示，MVP 不要求用户名唯一。
- 邮箱标准化后必须唯一，不能重复注册。
- 用户登录时使用邮箱和密码，不使用用户名登录。
- 密码必须以安全哈希保存，不能明文存储。
- 登录失效后，受保护操作返回未登录状态，界面引导用户重新登录。

#### USR-02 个人信息

- 用户可以查看和修改用户名、头像等非敏感基本信息。
- 用户 ID、注册时间等系统字段不可修改。
- 修改邮箱、密码找回、账号注销可以放入第二阶段。

#### USR-03 项目邀请

- 项目负责人只需输入邮箱创建邀请。
- 只能邀请已注册用户；邮箱未注册时直接提示失败。
- 受邀用户接受邀请后默认成为编辑成员，项目负责人之后可以将其调整为审核者。
- 邀请状态包括：待接受、已接受、已拒绝、已过期。
- 已是项目参与者的邮箱不能被重复邀请。
- 同一邮箱存在有效待处理邀请时，不重复创建邀请。
- 邀请不能由项目负责人撤销；错误邀请只能由受邀用户拒绝或等待过期。
- 站内不设置独立邀请中心，用户直接在邀请通知中接受或拒绝。

### 5.2 项目管理

#### PRJ-01 创建与查看项目

- 已登录用户可以创建项目，并自动成为该项目负责人。
- 项目至少包含：项目 ID、名称、简介、状态、负责人、创建时间、更新时间。
- 项目名称允许重复，系统通过不可变的项目 ID 区分项目。
- 用户只能查看自己参与的项目；直接访问无权项目的 URL 也不能绕过权限。

#### PRJ-02 项目成员管理

- 仅项目负责人可以邀请、移除成员和修改角色。
- 项目负责人身份在项目生命周期内不可转让、不可修改。
- 项目负责人不能离开项目，也不能将自己移除。
- 被移除用户立即失去项目、记录、附件、搜索和导出权限。
- 如果待移除用户创建了尚未完成的有效记录，则不能将其移除；该用户必须先完成或删除这些记录。
- 如果待移除用户是审核中记录的指定审核人，移除操作必须同时为这些记录重新指定合法审核人。
- 将编辑成员改为审核者前，其创建的所有有效记录必须已经完成；将审核者改为编辑成员时，如存在待审核任务，角色变更必须同时完成审核人重新指派。
- 已完成记录中保留原创建者和审核人的历史身份，不因成员离开而改变。

#### PRJ-03 项目状态

项目状态只有两种：

| 状态 | 允许的操作 |
|---|---|
| 进行中（ACTIVE） | 按角色执行创建、编辑、审核、成员管理等操作 |
| 已归档（ARCHIVED） | 所有参与者仅可查看和搜索记录、下载附件、导出已完成记录报告 |

归档规则：

- 仅项目负责人可以归档。
- 项目中所有未删除实验记录都必须处于“已完成”状态才能归档。
- 只要存在进行中、审核中或需修改记录，就不允许归档，并明确列出阻止归档的未完成记录。
- 项目没有任何未删除实验记录时，视为不存在未完成实验，允许归档。
- 项目归档时，尚未处理的邀请自动过期，对应通知保留但不能继续接受。
- 归档不会修改实验记录原有状态。
- 归档后不能创建或编辑记录、上传或删除附件、执行审核、邀请或移除成员。
- 归档是不可逆操作，不支持取消归档。
- MVP 不提供项目永久删除，以免产生级联删除、追溯丢失和误操作问题；第一版以归档代替删除。

### 5.3 实验记录

#### REC-01 基本字段

每条实验记录至少包含以下字段：

| 字段 | 规则 |
|---|---|
| 实验名称 | 初始创建时必填 |
| 所属项目 | 创建时由系统确定，之后不可跨项目移动 |
| 实验类型 | 初始创建时必填，可使用文本或预设选项 |
| 实验日期 | 初始创建时必填，默认当天 |
| 记录创建者 | 系统设置为当前用户，创建后不可修改或转交 |
| 实验目的 | 初始创建时必填 |
| 状态 | 由系统根据审核流程维护，用户不能直接修改 |
| 创建者、创建时间 | 系统维护，不可修改 |
| 最后修改人、修改时间 | 每次成功保存后由系统更新 |

创建操作只有在上述基本字段全部填写并校验通过后才成功，随后记录进入进行中状态。进行中表示基本信息已经完整，但模板字段、正文、结果或附件仍可继续补充；提交审核时再校验模板中标记为必填的内容。

界面与字段结构补充规则：

- 系统固定必填字段仅包括实验名称、所属项目、实验类型、实验日期、记录创建者和实验目的。
- “材料与试剂”“实验步骤”“实验结果”“结论与讨论”等内容不作为系统固定必填字段，也不强制拆分为固定章节。
- 用户选择模板创建记录时，在固定字段之外展示该模板定义的自定义字段；是否必填由模板字段配置决定。
- 固定字段和模板字段之外必须提供自由正文编辑区，允许用户使用富文本形式自由组织实验过程、数据、结果、讨论及其他补充内容。
- 新建记录前先选择所属项目以及空白记录、系统模板或个人模板；进入编辑器后不能切换所属项目或模板结构。

#### REC-02 状态设计

建议使用以下四个业务状态：

| 状态 | 含义 | 是否可编辑 |
|---|---|:---:|
| 进行中（IN_PROGRESS） | 正在填写，尚未提交 | 是 |
| 审核中（IN_REVIEW） | 已生成提交快照，等待指定审核人处理 | 否 |
| 需修改（CHANGES_REQUESTED） | 审核人已退回，等待创建者修改 | 是 |
| 已完成（COMPLETED） | 审核通过，流程结束 | 否 |

状态转换如下：

| 当前状态 | 操作 | 执行者 | 下一状态 | 关键条件 |
|---|---|---|---|---|
| 无 | 创建记录 | 项目负责人或编辑成员 | 进行中 | 基本字段完整，当前用户成为记录创建者 |
| 进行中 | 保存记录 | 记录创建者 | 进行中 | 保存不改变业务状态 |
| 进行中 | 提交审核 | 记录创建者 | 审核中 | 模板必填内容完整，指定合法审核人 |
| 审核中 | 因审核权限失效重新指派 | 项目负责人 | 审核中 | 原审核人因角色变化或被移除而失去审核权限 |
| 审核中 | 退回修改 | 指定审核人 | 需修改 | 必须填写审核意见 |
| 需修改 | 保存修改 | 记录创建者 | 需修改 | 保存不改变业务状态 |
| 需修改 | 再次提交 | 记录创建者 | 审核中 | 创建新的提交快照和审核轮次 |
| 审核中 | 审核通过 | 指定审核人 | 已完成 | 审核结论对应当前提交快照 |

补充规则：

- “保存”“暂存”和“自动保存”都是数据持久化动作，不是实验记录状态。界面统一使用“保存”；是否增加自动保存属于交互实现选择。
- 自动保存不能在每次输入时生成一条历史版本，否则会产生大量无意义版本。
- 每次提交审核时生成一份不可变的提交快照，并递增修订号，例如 `R1`、`R2`。
- 审核者查看和审核的是该次提交快照；记录进入审核中后，包括创建者在内的任何用户都不能修改记录内容、模板字段或附件。
- 指定审核人在仍具有审核权限时不可更换。
- 只有审核人因角色变化或被移除而失去审核权限时，项目负责人才可以重新指派审核人；权限变化和重新指派应在同一事务中完成。
- 重新指派不会修改实验记录、提交快照或审核轮次。
- 退回后可以继续编辑当前工作副本；再次提交会生成新的快照，不覆盖上一轮审核材料。
- 退回修改必须填写意见；审核通过时审核意见可以选填。
- 提交后不支持撤回；记录只能由审核人退回修改或审核通过。
- 同一次提交只能产生一个最终审核结果。重复点击、并发审核或过期页面操作必须被识别并拒绝。
- 已完成记录保持只读；当前项目范围内不考虑重新开启、修改或修正。
- “已完成”表示记录完成审核流程，不代表实验结果成功；实验结果应在模板字段中单独记录。

#### REC-03 查看、编辑与并发

- 所有项目参与者都可以查看项目内所有未删除记录，包括其他用户的进行中和需修改记录。
- 记录列表和详情页必须显著展示状态，避免将未完成内容误认为已完成记录。
- 审核者可以在普通记录列表查看全部记录，但“待我审核”列表只展示明确指派给自己且仍处于审核中的记录。
- 只有记录创建者可以编辑自己的记录；记录创建者身份不可修改，也不支持将记录转交给其他用户。
- 保存请求应携带版本号或最后更新时间；如果记录已被其他页面更新，系统返回冲突提示，不能静默覆盖新内容。
- 网络保存失败时界面必须明确提示，不能显示为已保存。
- 用户离开存在未保存内容的页面时，应进行离开确认。

#### REC-04 删除

- MVP 使用软删除，不直接物理删除数据库记录和附件对象。
- 只有记录创建者可以删除自己处于进行中或需修改状态的记录。
- 项目负责人不能删除其他用户创建的记录。
- 审核中记录不能删除。
- 已完成记录不能删除。
- 已删除记录不出现在普通列表、搜索和报告中，直接访问时也不能继续下载附件。
- 回收站和恢复入口放入第二阶段，但底层数据应保留追溯能力。

### 5.4 实验模板

#### TPL-01 模板类型

- 空白记录：使用系统默认字段创建。
- 系统模板：由系统预置，所有用户可查看和使用，普通用户不能修改。
- 个人模板：由用户创建，仅模板所有者管理，保存在“我的模板”中。
- 项目共享模板属于第二阶段，不与个人模板混用。

#### TPL-02 模板字段

MVP 支持以下字段类型：

- 单行文本。
- 多行文本。
- 数字。
- 日期。
- 单选或下拉选项。
- 图片或文件字段，实际文件仍通过附件模块保存。

每个字段至少具有：字段标识、显示名称、字段类型、是否必填、排序、提示文字和默认值。

模板规则：

- 系统固定字段和模板自定义字段分开保存；状态、创建时间等系统字段不能被模板覆盖。
- 无论选择空白记录还是模板，创建前都必须完成实验记录的全部基本字段。
- 个人模板名称在同一用户范围内应保持唯一，空白名称不能保存。
- 使用模板创建记录时复制模板结构快照。
- 修改、重命名或删除模板不会影响已经创建的记录。
- 被删除模板不能继续创建新记录，但历史记录仍可查看；其中已完成记录仍可导出。
- MVP 不支持嵌套字段、条件显示、公式计算和可重复字段组。

### 5.5 附件管理

#### ATT-01 上传与查看

- 只有记录创建者可以在进行中或需修改状态上传附件。
- 所有项目参与者都可以查看附件元数据并下载有权记录的附件。
- 附件至少展示：原始文件名、类型、大小、上传者、上传时间。
- 同名附件可以存在，系统使用不可变附件 ID 和存储键区分，不能直接使用用户文件名作为存储路径。

#### ATT-02 删除与保留

- 在记录可编辑时，只有记录创建者可以删除附件。
- 审核中和已完成状态不能添加或删除附件。
- 附件删除使用软删除，并记录删除人和删除时间。
- 已进入提交快照的附件即使后来从工作副本移除，也必须为历史审核材料保留底层文件。

#### ATT-03 文件安全与限制

MVP 建议采用以下默认限制，并允许通过配置调整：

- 单文件最大 20 MB。
- 单条记录附件总量最大 200 MB。
- 允许常见图片、PDF、文本、CSV、Office 文档和压缩包。
- 禁止可执行文件、脚本文件和明显危险的扩展名。
- 同时校验扩展名和 MIME 类型，文件存储在不可被匿名直接访问的位置。
- 下载必须经过登录和项目权限校验。
- 文件名和可预览内容必须进行安全转义，防止脚本注入。


### 5.6 搜索

#### SRCH-01 搜索中心（MVP）

- 搜索中心搜索当前用户有权访问的全部项目，不在项目详情页提供单独搜索入口。
- 搜索范围包括：实验名称、实验目的、正文、文本型模板字段、实验类型和附件文件名。
- MVP 不检索 PDF、Word、Excel、图片等附件内部内容。
- 支持按项目、项目状态、记录状态、记录创建者、实验类型、实验日期或更新时间筛选。
- 默认按相关性和最近更新时间排序，并提供分页。
- 空关键词配合筛选条件时可以返回筛选结果；关键词和筛选均为空时展示默认记录列表。
- 结果中必须明确显示所属项目。
- 已归档项目中的记录仍可以被项目参与者搜索。
- 搜索结果必须在后端按项目成员关系过滤，不能先搜索全部数据再依赖前端隐藏。
- 无权项目、已退出项目和已删除内容不能出现在结果、数量统计或搜索建议中。

### 5.7 审计与历史版本

#### AUD-01 基础审计（MVP）

系统至少记录以下事件：

- 项目创建、信息修改和归档。
- 邀请创建、接受、拒绝或过期，成员加入、移除和角色变更。
- 实验记录创建、提交、退回、通过和软删除。
- 附件上传和删除。
- 站内通知生成和审核任务重新指派。
- 报告导出。

项目详情中的“时间线”是面向参与者展示的审计事件子集，并不等同于完整审计日志。时间线应重点展示项目创建、成员加入或角色变化、实验记录创建、提交审核、退回修改和审核通过等项目协作事件；附件上传与删除仍需写入底层审计日志，但不在项目时间线中展示。

每条审计事件至少包含：事件类型、操作者、对象类型、对象 ID、发生时间和必要的上下文信息。审计事件应只追加，不允许普通用户修改或删除。

对于普通保存，MVP 至少维护最后修改人和最后修改时间；不必为每次自动保存生成完整内容快照。

#### AUD-02 历史版本（第二阶段）

- 向用户展示每次提交审核产生的不可变快照。
- 支持查看版本详情和相邻版本差异。
- 恢复历史版本时不能覆盖历史数据，而应基于选中版本创建新的进行中修订。
- 已完成版本始终保留，不能因恢复旧版本而改变原审核结论。

### 5.8 报告预览与导出

#### RPT-01 单条记录报告（MVP）

- 只有已完成记录可以进入报告预览和导出流程。
- 报告包含固定字段、模板字段、正文、图片、附件清单、创建者和审核信息。
- 报告使用审核完成的不可变快照，并展示审核人和审核时间。
- PDF 中可嵌入适合展示的图片；其他二进制附件只列出名称、大小等信息，不强制嵌入。
- Markdown 导出包含正文和附件清单；附件实体是否打包为 ZIP 可在后续版本增加。
- 所有项目参与者均可预览和导出有权查看的已完成记录。
- 导出动作写入审计日志，生成失败时不能留下可被误认为成功的空文件。

#### RPT-02 项目报告与结构化导出（第二阶段）

- 按筛选条件组合多条已完成实验记录生成项目报告。
- 支持目录、记录排序和封面信息。
- Excel 用于导出记录元数据和结构化字段，不作为长文本实验报告的主要格式。

### 5.9 站内通知与审核提醒

#### NTF-01 通知规则（MVP）

- 导航栏展示未读数量，用户可以查看通知列表并标记已读。
- 项目邀请直接在邀请通知中接受或拒绝，不设置独立邀请中心。
- 标记已读不等于处理邀请或审核任务。
- 点击通知时重新校验权限和对象状态；重复业务请求不得生成重复通知。

| 触发事件 | 接收人 | 通知结果 |
|---|---|---|
| 项目邀请创建 | 已注册的受邀用户 | 在通知中接受或拒绝 |
| 项目邀请被接受或拒绝 | 项目负责人 | 告知邀请处理结果 |
| 项目成员角色被调整或被移除 | 被调整用户 | 告知新的项目身份或访问权限变化 |
| 实验记录提交审核 | 指定审核人 | 提醒存在新的待审核记录 |
| 原审核人失去审核权限并重新指派 | 原审核人和新审核人 | 移除旧任务并告知新的审核指派 |
| 审核退回修改 | 记录创建者 | 提醒查看审核意见并修改记录 |
| 审核通过 | 记录创建者 | 提醒记录已进入已完成状态 |

#### NTF-02 审核提醒（MVP）

- 提交审核后立即通知指定审核人，并加入“待我审核”列表。
- 任务退回、通过或因权限变化重新指派后，从原审核人的待办列表移除。
- 已读但未处理的任务仍保留在“待我审核”列表。
- MVP 不实现定时重复催办、邮件、短信或浏览器推送。

- 所有已登录用户都可以创建和管理自己的个人模板。
- 是否能在某项目中使用模板创建记录，取决于该用户是否拥有该项目的记录创建权限。

## 7. 核心业务流程

### 7.1 创建项目与邀请成员

1. 用户填写用户名、唯一邮箱和密码完成注册，并使用邮箱和密码登录。
2. 用户创建项目并自动成为项目负责人。
3. 项目负责人输入已注册用户的邮箱发出邀请，不指定角色。
4. 受邀用户直接在邀请通知中接受或拒绝；接受后默认成为编辑成员。
5. 如需让该用户承担审核工作，项目负责人再将其角色调整为审核者。
6. 重复邀请、过期邀请或已加入项目的邀请被系统拦截。

### 7.2 创建、填写和审核实验记录

1. 项目负责人或编辑成员先选择一个自己拥有记录创建权限的进行中项目。
2. 用户选择使用空白记录、系统模板或个人模板作为记录结构来源，随后进入记录编辑器；进入编辑器后不能切换所属项目或模板结构。
3. 用户填写完整的实验名称、类型、日期、目的等系统固定必填字段，创建成功后成为该记录唯一且不可变的创建者。材料与试剂等内容不属于系统固定必填字段。
4. 记录创建者继续填写模板字段，并在自由正文编辑区记录实验过程、数据、结果和讨论，按需上传附件并保存进行中记录。
5. 创建者准备提交时再选择合法审核人；编辑和保存阶段不预先绑定审核人。
6. 创建者完成模板必填内容后提交审核。
7. 系统生成不可变提交快照，记录进入审核中并锁定编辑。
8. 指定审核人收到站内通知，任务进入“待我审核”列表。
9. 审核人选择：
   - 退回修改：填写意见，记录进入需修改状态。
   - 审核通过：记录进入已完成状态。
10. 系统将退回或通过结果通过站内通知发送给记录创建者。
11. 记录被退回后，创建者修改并再次提交，形成新的审核轮次。

### 7.3 搜索中心与导出

1. 用户进入搜索中心，在有权访问的全部项目中进行搜索。
2. 系统在用户权限范围内返回结果，并支持关键词和筛选条件。
3. 用户进入已完成记录详情，预览审核完成的快照。
4. 用户导出 PDF 或 Markdown，系统记录导出事件；未完成记录不提供报告导出。

### 7.4 项目归档

1. 项目负责人发起归档。
2. 系统检查所有未删除实验记录是否均为已完成状态。
3. 如果存在进行中、审核中或需修改记录，则拒绝归档并列出未完成记录。
4. 全部记录均已完成后，系统归档项目。
5. 项目进入只读状态，所有参与者仍可查看、搜索、下载和导出。

## 8. 重点边界与异常场景

| 场景 | 处理规则 |
|---|---|
| 移除创建了未完成记录的成员 | 阻止移除，直到其记录全部完成或被创建者删除 |
| 项目负责人尝试离开、移除自己或转让身份 | 拒绝操作 |
| 移除当前指定审核人 | 移除操作必须同时重新指派合法审核人 |
| 将有未完成记录的成员改为审核者 | 阻止角色变更，直到其创建的记录全部完成或被删除 |
| 用户邀请自己或已加入成员 | 拒绝创建邀请并给出明确提示 |
| 被邀请邮箱尚未注册 | 拒绝创建邀请并提示该邮箱尚未注册 |
| 负责人误发邀请 | 邀请不能撤销，只能由受邀用户拒绝或等待过期 |
| 项目归档时仍有待接受邀请 | 邀请自动过期，对应通知不能继续接受 |
| 记录创建者选择自己审核 | 禁止提交 |
| 项目中没有合法审核人 | 禁用提交并提示项目负责人邀请成员或设置审核者 |
| 审核人仍具有审核权限时尝试更换 | 拒绝操作，维持原指定审核人 |
| 审核中继续编辑、删除或增删附件 | 拒绝操作，只能等待审核通过或退回修改 |
| 审核者打开旧页面后提交结论 | 校验记录状态、审核轮次和版本号，过期操作返回冲突 |
| 用户快速重复点击提交或审核 | 接口应具备幂等性，只产生一次状态转换 |
| 两个页面同时编辑同一记录 | 使用乐观锁检测冲突，禁止后保存内容静默覆盖先保存内容 |
| 保存过程中网络中断 | 保留未保存提示，允许重试，不能显示“已保存” |
| 初始基本字段缺失 | 创建失败并定位缺失字段，不生成不完整记录 |
| 模板在记录创建后被修改或删除 | 已有记录继续使用创建时保存的结构快照 |
| 上传同名附件 | 允许存在，以附件 ID 区分，并展示上传时间等信息 |
| 上传空文件、超限文件或伪造类型 | 校验失败，不创建有效附件记录，并清理临时文件 |
| 上传中断 | 标记为失败并允许重试，未完成文件不能出现在附件清单 |
| 已提交附件后来被移除 | 历史提交快照仍保留原附件及其访问能力 |
| 归档时存在进行中、审核中或需修改记录 | 阻止归档，并列出未完成记录 |
| 已完成记录发现错误 | 当前范围不提供修改、重新开启或修正操作 |
| 重复生成同一站内通知 | 使用业务事件唯一标识去重，接口重试不能生成重复通知 |
| 从旧通知访问已经失效的任务 | 重新校验状态和权限，提示任务已处理或不可访问 |
| 非项目成员猜测到项目或附件 URL | 后端权限校验，不能泄露或下载内容 |
| 用户离开项目后使用旧链接 | 所有项目内容、附件、搜索和导出立即不可访问 |
| 尝试导出未完成记录 | 拒绝导出；报告只使用已完成记录的审核快照 |
| 浏览器与服务器时区不同 | 服务端统一保存 UTC，界面按用户时区显示 |

## 9. 初步数据对象

这不是最终数据库表设计，但后续建模时至少需要区分以下对象：

| 对象 | 主要职责 |
|---|---|
| User | 用户名、唯一邮箱、密码哈希和个人信息 |
| Project | 项目基本信息、状态和不可变的项目负责人 |
| ProjectMember | 用户与项目的成员关系及角色 |
| ProjectInvitation | 邀请邮箱、邀请项目、状态和有效期；接受后固定以编辑成员身份加入 |
| ExperimentRecord | 当前工作副本、不可变创建者和业务状态 |
| RecordTemplate | 系统模板或个人模板的基本信息 |
| TemplateField | 模板字段定义；也可在早期版本中使用受控 JSON 结构 |
| RecordFieldValue | 某条记录各模板字段的值；MVP 也可使用经过模式校验的 JSON 保存 |
| RecordRevision | 每次提交审核时生成的不可变内容快照 |
| Review | 一轮审核的修订号、审核人、结论、意见和时间 |
| Attachment | 文件元数据、存储键、所属记录和软删除信息 |
| Notification | 接收人、通知类型、关联对象、创建时间和已读时间 |
| AuditEvent | 只追加的关键操作记录 |

报告可以在 MVP 中按需生成，不必先设计可编辑的 Report 实体；如后续需要保存报告配置或异步导出任务，再增加对应对象。

## 10. 非功能性要求

### 10.1 安全

- 所有项目、记录、附件、搜索和导出接口均在后端进行身份与权限校验。
- 密码安全哈希保存，登录凭证设置有效期；项目邀请记录按照有效期自动过期。
- 富文本、Markdown、文件名和用户输入必须进行校验与安全转义。
- 文件不能保存在可匿名猜测并直接访问的公开路径。
- 敏感配置通过环境变量提供，不写入代码仓库。

### 10.2 数据一致性

- 提交审核、审核结论以及因权限变化产生的审核人重新指派使用数据库事务。
- 状态转换必须校验当前状态，不能由客户端任意指定目标状态。
- 保存和审核使用版本号进行乐观并发控制。
- 软删除数据默认不参与普通查询，但仍保留审计关联。
- ID 使用稳定的不可变标识；展示名称可以修改但不能作为关联依据。

### 10.3 性能与可用性

- 项目、记录、搜索结果和审计列表均使用分页，建议默认每页 20 条。
- 普通操作应显示加载、成功、失败、空数据和无权限状态。
- 上传和导出显示进度或处理中状态，防止用户重复操作。
- 桌面浏览器优先，同时保证常见平板宽度下能够基本使用。

### 10.4 API 错误语义

后续 API 设计应至少区分：

- 未登录。
- 已登录但无权限。
- 资源不存在。
- 参数或必填项校验失败。
- 当前状态不允许该操作。
- 记录版本过期或并发冲突。
- 文件限制或导出失败。

界面应根据错误类型给出可执行的下一步，而不是统一显示“操作失败”。

## 11. MVP 验收闭环

当系统能够稳定完成以下场景时，可以认为第一版核心功能闭环成立：

1. 用户 A、B、C 分别使用用户名、唯一邮箱和密码注册，并通过邮箱和密码登录。
2. 用户 A 创建项目，按邮箱邀请已注册的 B 和 C；两人在邀请通知中接受后成为编辑成员，未注册邮箱无法被邀请。
3. 用户 A 将 C 的项目角色调整为审核者，C 收到角色变更通知。
4. 用户 B 填写完整基本字段后创建记录并上传附件；A 和 C 可以查看进行中记录，但不能修改。
5. B 提交给 C 后生成修订 `R1`，内容和附件被锁定且不能撤回；C 收到审核通知。
6. C 退回后 B 修改并再次提交；C 审核通过后记录进入已完成并保持只读。
7. 用户能够在搜索中心搜索所有有权项目；只有已完成记录可以导出 PDF 或 Markdown。
8. 存在进行中、审核中或需修改记录时不能归档；全部有效记录均已完成后才能归档，归档后不能取消。
9. 非项目用户无法查看记录、搜索内容或下载附件。
10. 系统保留邀请、角色变更、审核、附件、通知和导出的关键审计记录。

## 12. MVP 核心约束

- 项目负责人不可转让身份、离开项目或取消归档。
- 记录状态为进行中、审核中、需修改、已完成；提交后不能撤回。
- 每次提交生成不可变快照，审核中和已完成记录不可编辑。
- 记录仅由不可变创建者管理，项目内其他用户只读。
- 指定审核人在权限不变时不可更换；失去审核权限时才允许重新指派。
- 邀请只面向已注册邮箱，在通知中接受或拒绝，不能撤销。
- MVP 实现搜索中心、站内通知和审核待办。
- 项目仅在所有有效记录均已完成时才能归档，且归档不可逆。
- 记录和附件使用软删除；只有已完成记录支持 PDF 和 Markdown 报告导出。
