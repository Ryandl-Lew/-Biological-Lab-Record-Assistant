# 03：批次二——项目、成员、邀请与归档

## 本批次目标

实现真实项目协作边界：用户只能看到自己参与的项目；项目负责人可邀请已注册用户、管理角色和成员；受邀用户在通知动作中接受或拒绝；项目满足条件后可不可逆归档。

通知表和审计表在本批次建立并写入事件，但完整通知中心、搜索和审计展示留到批次五。

## 1. 数据与服务

新增迁移和实体：

- `projects`
- `project_members`
- `project_invitations`
- `notifications`
- `audit_events`

创建项目必须在同一事务：

1. 创建 `Project(status=ACTIVE, owner=currentUser)`。
2. 创建 `ProjectMember(role=OWNER)`。
3. 写 `PROJECT_CREATED` 审计事件。

任何一步失败全部回滚。

## 2. 项目接口与规则

### 2.1 列表和详情

- `GET /projects` 只返回当前用户参与的项目，支持 `keyword`、`status`、分页。
- `GET /projects/{id}` 校验成员关系；返回当前用户角色和可执行能力 flags。
- 项目名称允许重复，前端不得假设名称唯一。
- 项目详情统计在数据库聚合，不能写死完成率和记录数。

### 2.2 创建

- `POST /projects`：名称必填，简介可设合理长度上限。
- 当前用户自动成为唯一 OWNER。

### 2.3 归档

- `POST /projects/{id}/archive`，只允许 OWNER。
- 查询所有未软删除记录；只要存在非 `COMPLETED` 记录即返回 409，并在结构化字段中列出阻塞记录 ID、名称和状态。
- 没有记录时允许归档。
- 同一事务把项目设为 `ARCHIVED`、所有 PENDING 邀请设为 `EXPIRED`、写通知和审计。
- 重复归档应返回当前已归档结果或明确幂等成功，不能产生重复事件。
- 不提供取消归档、删除项目或负责人转让接口。

批次二尚无记录表时，可以先通过抽象 `ProjectArchiveGuard` 返回无阻塞；批次三接入真实查询并补测试。不要写死永久允许。

## 3. 邀请流程

### 3.1 创建邀请

`POST /projects/{projectId}/invitations`

- 仅 ACTIVE 项目的 OWNER。
- 输入注册邮箱，服务端标准化后查用户。
- 未注册邮箱返回可理解错误，不创建占位用户。
- 不能邀请自己、现有成员或已有有效 PENDING 邀请的用户。
- 邀请默认 7 天过期，可由配置控制。
- 创建通知 `PROJECT_INVITATION`，payload 含 invitationId/projectId/actions。
- 邀请不能由 OWNER 撤销，不创建撤销接口。

### 3.2 接受/拒绝

- 只有邀请对应的受邀用户能操作。
- 接受在同一事务创建 `ProjectMember(role=MEMBER)`、设置邀请 ACCEPTED、通知 OWNER、写审计。
- 拒绝设置 REJECTED、通知 OWNER、写审计。
- 已处理或过期邀请不能再次处理；重复请求不得创建重复成员。
- 项目已归档时邀请视为 EXPIRED，不能接受。

## 4. 成员角色管理

### 4.1 列表

- `GET /projects/{id}/members` 对全部项目参与者可见。
- 返回角色、加入时间、最近活跃和基于规则生成的权限摘要。
- 不要返回全局敏感字段。

### 4.2 修改角色

`PATCH /projects/{projectId}/members/{userId}/role`

- 仅 OWNER；不能修改 OWNER 自己。
- 目标只允许 MEMBER 与 REVIEWER 互转。
- MEMBER → REVIEWER：其创建的所有未删除记录必须全部 `COMPLETED`。
- REVIEWER → MEMBER：若其仍是 PENDING review 的指定审核人，请求必须携带每条记录的新合法 reviewer，且同一事务重指派。
- 指定的新 reviewer 必须是项目 OWNER 或 REVIEWER、不能是对应记录创建者。
- 成功后通知目标用户，必要时通知新旧审核人和创建者，并写审计。

批次二先定义 `ReviewAssignmentGuard` 接口；没有 review 表时实现空检查。批次四必须替换为真实逻辑并补回归测试。

### 4.3 移除成员

`POST /projects/{projectId}/members/{userId}/remove`

- 仅 OWNER；不能移除 OWNER 自己。
- 若目标创建了未完成有效记录，阻止并返回阻塞记录列表。
- 若目标是 PENDING review 审核人，必须随请求完成全部合法重指派。
- 移除、重指派、通知、审计在同一事务。
- 被移除用户之后访问项目、记录、附件、搜索或导出立即失败。

批次二同样用明确的 guard 接口占位，后续接真实记录模块；禁止永久返回“无阻塞”的匿名 lambda。

## 5. 前端项目页改造

### 5.1 项目列表

- `ProjectsPage` 使用服务端分页和筛选。
- 新建项目弹窗改为受控表单并调用真实接口。
- 创建成功跳转项目详情或刷新列表；失败保留输入。
- 只显示 `ACTIVE`、`ARCHIVED` 两种状态。

### 5.2 项目详情

- 删除同文件 `LegacyProjectDetailPage`。
- 根据 `currentUserRole` 和项目状态渲染操作。
- 成员 Tab：OWNER 可邀请、改角色、移除；其他角色只读。
- 角色变更/移除被阻塞时，弹窗展示具体记录与需要重指派的审核任务。
- “待审核”先隐藏或留到审核批次接入，不得错误显示项目全部审核中记录。
- 项目附件区不能上传独立项目附件。若保留卡片，改名为“记录附件汇总”并在批次四接只读聚合；本批次可隐藏。
- OWNER 看到“归档项目”；二次确认明确不可恢复。阻塞时显示记录列表。

### 5.3 邀请动作临时入口

批次五才完成全局通知中心，但本批次必须有可测试入口：

- 顶栏通知下拉从真实 `/notifications` 读取邀请通知。
- 邀请通知内展示接受/拒绝按钮。
- 操作后刷新项目列表和通知状态。

不要继续使用 `INITIAL_NOTIFICATIONS`。

## 6. 权限测试

后端集成测试至少覆盖：

- 非成员无法通过猜 URL 查看项目。
- MEMBER/REVIEWER 不能邀请、改角色、移除或归档。
- OWNER 不能邀请自己、未注册邮箱、已有成员或重复 pending 邀请。
- 邀请只能由受邀用户接受/拒绝；过期和归档后不可接受。
- 接受邀请只创建一个 MEMBER 关系。
- OWNER 不可被修改、移除或转让。
- 归档无记录项目成功；归档后所有写操作被拒绝。
- 通知和审计的 dedup key 在重复请求下不重复。

前端测试至少覆盖：

- 非 OWNER 不显示管理动作。
- 归档确认和阻塞记录展示。
- 邀请接受/拒绝会调用正确接口并更新 UI。

## 7. 人工验收

1. A 创建项目，在列表和详情都能看到 OWNER 身份。
2. A 邀请未注册邮箱失败；邀请 B 成功；重复邀请 B 失败。
3. B 登录后从通知接受，立即出现在项目成员中，角色为 MEMBER。
4. A 把 B 改为 REVIEWER；B 收到角色变化通知。
5. B 不能看到邀请、移除和归档按钮；直接调接口也返回 403。
6. A 归档空项目成功；归档后所有管理按钮消失且接口拒绝写入。
