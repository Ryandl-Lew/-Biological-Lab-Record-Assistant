# 06：批次五——通知、搜索、审计与工作台整合

## 本批次目标

把前四批次的业务事件整合为用户可处理的工作台：真实通知与未读状态、邀请动作、审核/修改待办、跨项目搜索、项目审计时间线和统一统计。

本批次不接真实邮件、短信、浏览器推送或 WebSocket。使用数据库事件 + 页面刷新/短轮询即可。

## 1. 通知中心

### 1.1 接口

- `GET /notifications?unreadOnly=&page=&size=`：只返回当前用户通知，按 `createdAt desc, id desc`。
- `PATCH /notifications/{id}/read`：只能标记自己的通知，幂等。
- `POST /notifications/read-all`：标记当前用户全部未读，幂等。
- 可提供 `GET /notifications/unread-count`，或在列表 meta 中返回未读数。

通知 DTO 必须包含：

- id、type、title、body、createdAt、readAt。
- `target`：受控的实体类型和 ID，不接受服务端返回任意外部 URL。
- `actions`：仅邀请通知在仍为 PENDING 时返回 `ACCEPT/REJECT`。
- `stale`：邀请过期、任务已处理或用户失权时为 true。

### 1.2 事件完整性

检查前面批次所有事件都真实产生通知，并由唯一 `dedup_key` 去重：邀请、邀请结果、角色变化、成员移除、审核指派、退回、通过、审核人重指派、项目归档。

通知创建失败不能让核心业务留下半成功状态。对同事务事件直接同事务写通知；若采用 outbox，必须在本批次完整实现，不留不可运行的半套架构。

### 1.3 前端

重写 `Topbar`：

- 删除 `INITIAL_NOTIFICATIONS`。
- 打开下拉时获取第一页，并显示真实未读数。
- 登录状态下每 15–30 秒轮询未读数，页面重新聚焦时立即刷新；组件卸载停止轮询。
- 点击普通通知：先标已读，再按受控 target 跳项目/记录。
- 邀请通知内直接接受/拒绝；动作前重新校验，处理后显示结果或失效原因。
- “全部已读”调用真实接口。
- 加载、空、失败和“查看更多”状态完整。

旧通知指向已处理审核、已归档邀请或用户已失权资源时，后端重新校验，前端提示“任务已处理或不可访问”，不能显示假成功。

## 2. 工作台

实现：

- `GET /dashboard/tasks`
- `GET /dashboard/summary`

### 2.1 待办来源

`tasks` 只包含真实可操作项：

- 当前用户创建且状态为 `CHANGES_REQUESTED` 的记录。
- 当前用户为指定审核人且仍为 PENDING review 的记录。
- 当前用户仍可处理的项目邀请。

删除现有 mock “课程提醒”等无业务来源内容，除非建立真实实体；MVP 不需要通用待办管理。

任务返回稳定 type、target ID、标题、项目、时间、修订号、操作文案和 stale 状态。前端不要根据本地全部记录自行猜待办。

### 2.2 统计

summary 可包含：参与项目数、我创建的进行中/需修改记录数、待我审核数、未读通知数。所有统计必须服从权限和软删除过滤。

### 2.3 页面

保留现有简洁工作台样式：

- 待办按“需修改 → 待审核 → 邀请”排序，再按时间。
- 每项跳到真实动作页面。
- 已处理任务刷新后消失。
- 空状态不显示 mock 数据。

## 3. 全局搜索

### 3.1 接口

`GET /search`

参数：

- `keyword`，trim 后可空；空关键词返回最近更新的有权内容或要求用户输入，二者选一并保持一致。
- `entityType=ALL|PROJECT|RECORD|TEMPLATE|MEMBER|ATTACHMENT`
- `projectId`
- `creatorId`
- `recordStatus`
- `page`、`size`

结果统一包含：

- `entityType`、`id`、`title`、`snippet`。
- `projectId/projectName`（适用时）。
- `status`、`updatedAt`（适用时）。
- 受控 target，不返回拼接好的任意 URL。

### 3.2 搜索实现

MVP 使用 MySQL 索引和参数化 LIKE/全文索引即可，不引入 Elasticsearch。

必须做到：

- 先以当前用户项目成员关系限定数据，再搜索。
- 记录搜索标题、code、实验类型、目的、`content_plain_text` 和文本型模板值。
- 项目搜索名称、简介。
- 成员搜索显示名和项目内邮箱，但只在双方共享的有权项目上下文出现。
- 附件只搜原始文件名/MIME 元数据，不读文件内容。
- 模板只搜系统模板和当前用户个人模板。
- 排除软删除、已失权项目和失效资源。
- 对 `%`、`_` 等 LIKE 通配符正确转义；限制 keyword 长度。
- 返回匹配摘要时转义用户内容，前端若高亮关键字不得使用未净化 HTML。

### 3.3 分页与类型计数

现有页面 Tab 显示类型计数。不要为了计数一次拉取全部结果。

可采用：

- 响应 meta 返回当前筛选条件下各实体类型计数；或
- Tab 切换时分别请求，全部 Tab 只显示总数。

无论选择哪种，列表必须服务端分页，默认 20。

### 3.4 前端页面

- 高级筛选全部接入 URL query，刷新/分享页面可保持条件。
- 搜索输入 debounce 300–500ms，并可按 Enter 立即搜索。
- 点击结果跳到精确实体：项目详情、记录详情、模板预览、项目成员 Tab、记录附件所在详情；不能只跳到列表首页。
- 附件结果打开所属记录并定位附件；不直接暴露未经校验的下载 URL。
- 加载、无结果、错误、分页完整。

## 4. 审计与项目时间线

### 4.1 后端

`GET /projects/{projectId}/audit-events`

- 仅项目参与者。
- 支持 eventType、actorId、日期范围、分页。
- 事件按时间倒序，记录 actor 展示快照或当前显示名；历史意义不能因成员被移除而消失。
- metadata 只包含展示需要的安全字段，不能返回 password、token、storageKey、完整正文或内部堆栈。
- 没有更新/删除审计接口。

审计写入检查：

- 对照 `01-domain-api-contract.md` 的事件清单补齐遗漏。
- 事件和业务变更尽量同事务。
- 对导出等流式操作，在成功生成响应前后采用明确策略：只有生成成功才写成功事件。

### 4.2 项目详情

- 现有“时间线”改为真实审计时间线。
- 默认展示可读中文描述、操作者、时间和对象。
- OWNER 可使用筛选；其他参与者也可查看项目审计。
- 不提供修改、删除、恢复事件按钮。

## 5. 项目中的附件汇总

产品模型不允许项目级附件，但现有项目详情有附件区域。可以保留为只读“记录附件汇总”：

- 后端按项目聚合未删除记录附件，仍通过记录成员权限校验。
- 每项显示所属记录并跳转该记录附件区。
- 不提供项目级上传、删除或恢复。
- 项目归档后仍可查看/下载有权附件。

若页面空间不合适，可完全移除该区域；禁止重新引入 project attachment 数据模型。

## 6. 导航与页面一致性

- Sidebar 只保留工作台、项目、记录、模板、搜索、个人中心。
- AI 助手、无路由 TeamPage 和其他非 MVP 入口移除。
- 所有页面使用同一状态/角色 label 映射。
- 项目、记录、模板、通知、搜索的 loading/error/empty 风格一致。
- mutation 成功后刷新相关列表、待办、未读数和详情，避免静态旧状态。
- 归档项目的所有写按钮禁用或隐藏，同时详情显示“只读归档”说明。

## 7. 测试要求

后端：

- 每种通知事件生成、dedup、只读权限、read/read-all 幂等。
- 旧通知动作重新校验状态和权限。
- dashboard 只返回当前用户真实可操作任务，已处理后消失。
- 搜索绝不返回无权项目、软删除或附件正文内容。
- 搜索各种筛选、分页、稳定排序和通配符转义。
- 被移除成员旧搜索/附件结果立即失效。
- 审计事件不可修改/删除，项目外用户不可读。
- 项目附件汇总只有记录附件且只读。

前端：

- 通知轮询启动/停止、未读计数、标记已读、邀请动作。
- 工作台任务跳转和处理后刷新。
- 搜索筛选写入 URL、分页、精确跳转。
- 审计时间线加载和筛选。

## 8. 人工验收

1. A 邀请 B 后，B 无需手动找项目即可在通知中接受。
2. B 提交 R1 后，C 的未读数和待办出现审核任务；处理后任务消失。
3. C 退回后，B 工作台出现“继续修改”，点击直达编辑器。
4. 搜索“PCR”能跨 B 有权项目找到项目/记录/模板/附件名，但找不到无权项目。
5. 从搜索附件结果进入正确记录并定位附件。
6. 项目时间线可看到邀请、角色变化、提交、审核、附件和导出事件。
7. 被移除用户刷新后，旧通知/搜索链接无法继续访问项目内容。
