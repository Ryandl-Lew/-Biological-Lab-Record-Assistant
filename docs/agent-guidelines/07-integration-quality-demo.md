# 07：批次六——集成清理、质量门禁与演示交付

## 本批次目标

不再新增产品范围，而是把前五批次整合成稳定可展示的 MVP：清除所有业务 mock 和假入口，补齐权限/状态/并发回归测试，提供确定性演示数据、E2E 主流程、启动文档和最终验收报告。

## 1. 全仓库清理

使用 `rg` 检查并处理：

- `mockResponse`、`mockProjects`、`mockRecords`、`INITIAL_NOTIFICATIONS`、静态 token、固定用户 ID。
- `TODO`、`FIXME`、`占位`、`静态原型`、无功能按钮。
- `Legacy*` 页面和重复实现。
- `observer`、`pending_review`、`rejected`、样品/试剂选择器等旧枚举。
- AI 助手导航和路由。
- 项目级附件上传或恢复/回收站入口。
- 硬编码日期、用户、审核人、项目统计和成功提示。

处理原则：

- MVP 内 TODO 必须实现或移除。
- 非 MVP TODO 可保留在独立 roadmap 文档，不能留作可点击入口。
- 如果 `frontend/src/mocks/data.js` 不再被引用，删除它。
- 删除无路由 `TeamPage`、重复 CSS 和未使用 import；不要误删仍被真实页面使用的通用组件。

## 2. 确定性开发/演示数据

提供仅 dev profile 启用的幂等 seed：

- A：`owner@example.com`
- B：`member@example.com`
- C：`reviewer@example.com`
- 可选 outsider：`outsider@example.com`
- 密码使用文档明确的开发密码，例如 `Demo123!`，只能存在于 dev seed/README，不用于生产 profile。
- 2–3 个系统模板。
- 一个可从零演示的空项目，以及可选的只读完成示例项目。

seed 必须：

- 重复启动不重复数据。
- 在生产 profile 默认关闭。
- 不绕过密码哈希和领域不变量。

## 3. 自动化测试分层

### 3.1 后端单元/领域测试

覆盖状态机和权限决策：

- 记录状态转换合法/非法路径。
- 审核人候选规则、自审禁止。
- 项目归档阻塞。
- 成员移除/改角色阻塞与重指派。
- 模板字段 schema 和快照。
- 附件状态权限。
- 通知 dedup 和审计事件映射。

### 3.2 后端集成测试

使用真实 MySQL 语义运行 Flyway，至少覆盖：

- 唯一索引和外键。
- 并发提交/审核、乐观锁。
- 事务回滚：角色变化 + reviewer 重指派、提交 revision + review + notification + audit。
- 软删除过滤及历史 revision 附件访问。
- 搜索权限和分页。
- PDF/Markdown 导出权限与内容来源。

### 3.3 前端组件/集成测试

覆盖：

- 认证恢复和 401。
- 项目/邀请/角色/归档表单。
- 模板字段编辑器。
- 记录首次创建、保存状态、离开提示、版本冲突。
- 提交/审核/附件预览/导出。
- 通知、待办、搜索 URL 筛选。

### 3.4 E2E

新增 Playwright，使用独立测试数据库和 API seed/reset 工具。至少编写：

1. `auth-profile.spec`：注册、邮箱登录、修改资料、退出。
2. `mvp-review-flow.spec`：A 创建项目 → 邀请 B/C → 接受 → C 变 REVIEWER → B 建模板和记录 → 上传 → R1 退回 → R2 通过 → 导出 → 归档。
3. `authorization.spec`：outsider 猜项目/记录/附件 URL 失败；OWNER 不能编辑他人记录；非指定 reviewer 不能审核。
4. `conflict-idempotency.spec`：双击提交/审核和两个页签保存冲突。

E2E 不得依赖测试执行顺序；每个 spec 独立准备数据或统一 reset。

## 4. 最终业务回归矩阵

| 产品能力  | 必须验证的成功路径                | 必须验证的失败/边界                         |
| --------- | --------------------------------- | ------------------------------------------- |
| 注册登录  | 邮箱注册、登录、刷新恢复、退出    | 邮箱重复、错误密码、过期 token              |
| 个人资料  | 修改显示名/头像                   | 修改只读字段、非法头像                      |
| 项目      | 创建、成员可见、空项目归档        | 非成员访问、非 OWNER 管理、归档有未完成记录 |
| 邀请      | 注册用户邀请、通知接受/拒绝       | 自邀、未注册、重复、过期、归档后接受        |
| 角色/移除 | MEMBER/REVIEWER 变更、合法移除    | OWNER 变更、未完成记录阻塞、审核重指派缺失  |
| 模板      | 系统模板使用、个人模板 CRUD/复制  | 改系统模板、重名、非法字段、删除后继续新建  |
| 记录      | 空白/模板创建、保存、查看、软删除 | 固定字段缺失、他人编辑、归档写入、版本冲突  |
| 附件      | 上传、预览图片/PDF、下载、软删除  | 超限/伪造类型、无权 URL、审核中删除         |
| 审核      | R1 退回、R2 通过                  | 自审、非指定审核、空退回意见、重复/旧页操作 |
| 通知/待办 | 未读、已读、邀请动作、任务消失    | 重复通知、旧任务、失权链接                  |
| 搜索      | 跨有权项目、筛选、分页、精确跳转  | 无权/软删除泄露、附件正文搜索               |
| 审计      | 关键事件时间线                    | 修改/删除审计、敏感 metadata                |
| 导出      | 完成记录预览、PDF、Markdown       | 未完成、非成员、使用错误 revision           |

矩阵中每一行至少有自动化测试或明确的人工验收记录；关键权限和状态机必须自动化。

## 5. 演示脚本

在根 README 提供 8–12 分钟可执行脚本：

### 场景 A：协作闭环

1. 使用 A 登录并创建“软件工程实践演示项目”。
2. 邀请 B、C；切换浏览器上下文让 B、C 从通知接受。
3. A 将 C 改为 REVIEWER。
4. B 创建个人模板，含“预期条带大小（NUMBER）”“实验结果（MULTI_LINE_TEXT）”“结果文件（FILE）”。
5. B 使用模板创建记录，填写富文本，保存并上传 PNG/PDF。
6. A 查看 B 的进行中记录但不能编辑。
7. B 提交给 C，生成 R1。
8. C 预览附件并退回；B 修改后提交 R2；C 通过。

### 场景 B：检索、导出和归档

1. 搜索记录关键字并通过筛选定位结果。
2. 查看项目审计时间线。
3. 导出 PDF/Markdown，打开确认中文和内容。
4. 演示存在未完成记录时归档被阻止；处理后归档成功。
5. 归档后尝试创建/编辑，展示只读约束。

### 场景 C：安全边界

1. outsider 访问复制的项目/记录/附件地址失败。
2. A 尝试编辑 B 的记录失败。
3. 非指定审核人尝试审核失败。

演示脚本同时列出备用数据和恢复方式，避免现场操作失误后只能重装数据库。

## 7. 构建与运行门禁

最终必须实际运行并记录结果：

```bash
docker compose up -d mysql
cd backend && ./mvnw test
cd backend && ./mvnw verify
cd frontend && npm ci
cd frontend && npm run lint
cd frontend && npm test -- --run
cd frontend && npm run build
cd frontend && npx playwright test
```

如果项目脚本名称不同，统一脚本后更新文档。不得以“预计通过”代替实际执行。

启动完整应用后至少执行一次 API/浏览器 smoke test：健康检查、登录、项目列表、上传预览、搜索、导出。

## 8. 性能与可用性底线

- 项目、记录、搜索、通知、审计默认分页 20。
- 为成员关系、记录 project/status/updated、通知 recipient/read/created、审计 project/created、附件 record/created 建索引。
- 普通列表避免 N+1；用投影/批量查询或 entity graph。
- 搜索和项目详情在演示数据规模下响应流畅；不要在前端拉全库再筛选。
- 上传和导出有处理状态，防止重复操作。
- 表单错误定位到字段；危险操作说明后果。

## 9. 最终安全检查

- 仓库扫描无真实密码、JWT Secret、数据库凭证和上传文件。
- 生产配置不启用 dev seed、H2 console、详细堆栈或宽松 CORS。
- 所有 ID 路径接口都有对象级授权测试。
- 富文本、文件名、Markdown、搜索 snippet 在展示/导出时安全转义。
- 上传目录不位于前端 public 或 Spring 静态资源目录。
- 预览/下载/导出每次重新授权，不依赖之前页面能否看到按钮。
- 错误日志不含 token、密码、二进制和完整敏感正文。

## 10. 最终交付报告格式

code agent 最后必须给出：

1. 已实现的 MVP 能力列表。
2. 关键架构和目录说明。
3. 数据库 migration 列表。
4. 实际执行的构建/测试命令及通过数量。
5. E2E 主流程结果。
6. 仍存在但不影响 MVP 演示的已知限制。
7. 明确声明未实现的第二阶段能力。
8. 从零启动和开始演示的最短步骤。

不得把未完成项隐藏在“后续优化”中。如果任一 MVP 验收闭环无法执行，应明确标记为阻塞，而不是宣布第一阶段完成。
