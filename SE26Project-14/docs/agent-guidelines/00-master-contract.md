# 00：第一阶段 MVP 总契约

本文件是所有开发批次的公共约束。若现有静态页面、mock 数据、参考项目或 agent 的实现偏好与本文件冲突，以 `docs/01-product-overview.md` 和本文件为准。

## 1. 目标与完成标准

目标不是继续制作静态原型，而是交付一套可本地部署、使用真实数据库、真实认证和真实文件的课程展示系统。

“完成”同时满足：

- 前端不再依赖 `frontend/src/mocks/data.js` 承担业务功能。
- 所有 MVP 按钮均有真实结果、明确禁用原因或被移除，不保留假成功交互。
- 后端对每个项目、记录、附件、搜索、导出接口执行身份和权限校验。
- 关键状态转换具备事务、幂等和并发冲突保护。
- 主演示闭环有自动化 E2E 覆盖，并可用三个演示账号手工复现。
- 项目可通过明确的 README 和环境变量示例启动，不依赖开发者机器上的隐式配置。

## 2. 需求真值与优先级

冲突时按以下优先级处理：

1. `docs/01-product-overview.md` 中的业务规则与 MVP 验收闭环。
2. `01-domain-api-contract.md` 中为了实现这些规则而固定的技术契约。
3. 本目录当前批次指南。
4. 现有 `frontend/` 的布局、视觉和页面信息架构。
5. 两个参考项目中被明确允许参考的局部实现。

现有页面用于保留视觉语言和页面入口，不是业务规则来源。不得为了少改页面而削弱产品文档中的权限、状态机或不可变快照。

## 3. 第一阶段范围

必须实现：

- 注册、邮箱登录、退出、会话恢复、个人资料维护。
- 项目创建、查看、成员邀请、接受/拒绝邀请、角色管理、成员移除、不可逆归档。
- 空白结构、系统模板、个人模板；个人模板完整 CRUD 和有序字段编辑。
- 记录创建、保存、富文本正文、模板字段、乐观锁、软删除。
- 附件上传、列表、下载、软删除，以及图片/PDF 内联预览。
- 单审核人流程：提交快照、退回修改、再次提交、审核通过。
- 站内通知、未读状态、邀请动作和审核待办。
- 跨有权项目的全局搜索、筛选、分页。
- 追加式审计事件和项目时间线。
- 已完成单条记录的 PDF、Markdown 预览/导出。

明确不实现：

- AI 助手、真实邮件、短信、WebSocket 实时协作。
- 项目共享模板、回收站 UI、历史差异/恢复、已完成记录重开。
- 项目级独立附件、Office/OCR 正文解析、附件内容全文检索。
- 多审核人、并行审核、多级审批。
- 库存、样品库、试剂库、仪器预约和生物信息学分析。

## 4. 指定参考项目的硬边界

### 4.1 `SE26Project-14-p5`：只参考附件预览形态

允许参考：

- `frontend/src/components/file/FileManager.jsx` 中“文件列表 → 图片/PDF 弹窗内联预览 → 下载/新窗口”的交互形态。
- `/files/{id}/preview` 使用正确 MIME 和 `Content-Disposition: inline` 的响应语义。
- Blob 下载、文件名解析、Object URL 释放、上传进度等纯文件交互细节。

禁止复制：

- 项目级附件上传和项目/记录二选一的附件归属模型。本项目附件只能归属实验记录。
- 回收站、恢复入口；它们属于第二阶段。
- `MOCK_USER_ID`、缺失权限校验、通过裸 URL 绕过 Bearer 认证的做法。
- 独立 Axios 客户端、与主 API 客户端分裂的认证方案。
- P5 的项目、记录、搜索、审核、导出或任何其他业务实现。

本项目预览必须通过统一认证客户端获取 Blob，再创建临时 Object URL。不能把需要 Bearer Token 的裸预览 URL直接赋给 `iframe src`。

### 4.2 `SE26Project-14-P3`：只参考模板创建方式

允许参考：

- 模板元数据与模板字段分离的结构。
- 一次创建模板时编辑有序字段列表；字段有稳定 key、标签、类型、必填、配置和排序。
- 模板卡片的查看、使用，以及个人模板的复制/编辑入口思路。

禁止复制：

- P3 的认证、项目、记录、搜索、审核等其他实现。
- P3 中尚未实现的 TODO 或 mock 行为。
- 仅保存 `template_id` 而不在记录创建时复制模板结构的做法。
- P3 中超出本项目 MVP 的字段类型，例如样品选择器、试剂选择器、嵌套表格。

## 5. 技术架构

### 5.1 仓库结构

保留现有前端，在根目录新增后端和部署文件：

```text
frontend/                 React SPA，延续现有 UI
backend/                  Spring Boot REST API
docs/                     产品文档与开发指南
compose.yml               MySQL 和可选的应用容器
.env.example              非敏感配置示例
README.md                 一键启动、测试和演示说明
```

### 5.2 前端

- React 18、Vite 5、React Router 6、Zustand、Tailwind，延续现有技术栈和视觉设计。
- 允许新增统一的 Axios 客户端、TipTap、DOMPurify、Vitest、Testing Library、Playwright。
- 所有 HTTP 请求必须通过一个共享客户端；统一注入 Token、解析错误、处理 401 和 Blob。
- Zustand 只存认证和轻量 UI 状态，不把整套服务端业务数据长期复制进全局 store。
- 表单必须是受控表单或由明确的表单库管理，不能依赖大量 `defaultValue` 造成保存数据与界面脱节。

### 5.3 后端

- Java 17、Spring Boot 3.x、Maven。
- Spring Web、Validation、Security、Data JPA、Flyway、MySQL 8、JWT、springdoc-openapi。
- 测试使用 JUnit 5、Spring Boot Test；集成测试优先使用 Testcontainers MySQL，至少保证 Flyway 与真实 MySQL 语义一致。
- 按业务包组织，例如 `auth`、`user`、`project`、`invitation`、`template`、`record`、`review`、`file`、`notification`、`search`、`audit`、`report`。
- Controller 只负责协议转换；权限、状态机和事务在 service/domain 层集中实现。

### 5.4 数据与时间

- 主键使用 UUID 字符串或原生 UUID，前后端都把 ID 当不可变字符串。
- 数据库存 UTC；API 返回 ISO-8601 UTC；前端按浏览器时区展示。
- 所有可并发修改的聚合根使用 `version` 乐观锁。
- 记录、附件、个人模板使用软删除；普通查询默认排除软删除数据。
- 审核快照、审核结论、审计事件只能追加，不能更新正文或物理删除。

## 6. 现有前端必须纠正的偏差

开发过程中必须主动修正，而不是兼容两套含义：

- 删除 `observer` 角色；只保留 `OWNER`、`MEMBER`、`REVIEWER`。
- 记录状态统一为 `IN_PROGRESS`、`IN_REVIEW`、`CHANGES_REQUESTED`、`COMPLETED`；删除 `pending_review`、`rejected` 等平行命名。
- 模板字段只保留单行文本、多行文本、数字、日期、单选/下拉、文件；删除样品/试剂选择器和通用嵌套表格。
- 项目详情中的“项目附件上传”改为“本项目记录附件汇总”只读视图，或从 MVP 页面移除上传入口。
- “待审核”只显示明确指派给当前用户的审核中记录，不能显示项目全部审核中记录。
- 登录只能使用邮箱，不再支持用户名登录。
- 移除侧栏 AI 助手入口和 `/ai` MVP 路由，或用关闭的 feature flag 完全隐藏。
- 删除同文件中的 `Legacy*` 页面实现、无路由死页面和重复 CSS，保留一个真实版本。
- 任何静态“成功”按钮、硬编码通知、固定个人资料、固定日期和占位预览都必须替换或移除。

## 7. 安全与权限底线

- 邮箱 trim + lowercase 后唯一；密码使用 BCrypt/Argon2，不记录明文和认证请求体。
- 所有富文本在服务端净化；禁止脚本、事件属性、危险 URL 和任意 iframe。
- 上传文件随机命名，存储路径不可由原文件名控制；校验大小、扩展名、MIME，阻止路径穿越。
- 附件和导出文件不能放在公开静态目录；每次预览/下载均重新校验当前项目权限。
- 前端禁用或隐藏只改善体验，不能作为授权依据。
- 无权资源避免泄露细节；统一返回 403 或按安全策略返回 404，但同一类接口必须一致。
- 日志不得输出密码、Token、附件二进制、完整富文本或敏感请求头。

## 8. Agent 工作纪律

每个批次都必须：

1. 先检查工作区和已有修改，保留与本任务无关的用户改动。
2. 先更新/补充测试，再实现或同步实现，不允许只靠手工点击。
3. 只实现当前批次；发现后续需求时留下明确接口和 TODO，不提前扩张范围。
4. 数据库变更只新增 Flyway migration，不能改写已经执行过的迁移。
5. 更新 OpenAPI、前端 domain model 和 API 封装，避免页面自行拼 URL。
6. 运行本批次列出的测试和构建命令。
7. 最终报告实际修改、测试输出、已知限制；不得把未验证内容写成已完成。

## 9. 通用 Definition of Done

- 正常、加载、空数据、校验失败、无权限、冲突、网络失败状态都有可理解的 UI。
- 关键操作有二次确认或明确后果提示，提交期间禁用重复点击。
- API 既有 happy path，也有至少一个权限失败和一个状态冲突测试。
- 列表使用分页；默认 20 条，并保持稳定排序。
- 新增页面在常见桌面和约 768px 宽度下可用。
- `frontend npm run build`、前端测试、`backend mvn test` 全部通过。
- 不存在业务 mock、静态假成功、默认测试 Token、硬编码用户 ID 或仓库中的真实密钥。
